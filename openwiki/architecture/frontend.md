# Nuxt Frontend Architecture

The frontend lives in `frontend/` and is a Nuxt 4 app (Vue 3, TypeScript, Vuetify, `@nuxtjs/i18n`, `@vite-pwa/nuxt`) with `ssr: false`, so it ships as a static single-page app. In production it is generated by `task ui:generate` (`pnpm generate` into `frontend/dist`) and served by the FastAPI SPA module (see [[app-lifecycle]]); in development `task ui` runs the Nuxt dev server on port 3000 against the backend on 9000.

## Directory layout

Under `frontend/app/`: `pages/` (routes such as login, shopping-lists, group, household, admin, user), `layouts/` (default, admin, basic, blank), `components/`, `composables/`, `lib/api/`, `middleware/`, `plugins/`, `lang/` (i18n) and `tests/`. Nuxt `components` auto-import is configured with `pathPrefix: false`, so a component's folder does not appear in its name.

### Component conventions

From `app/components/README.md`:

- `Domain/`: feature-specific components, prefixed with the domain name (for example `AdminDashboard`).
- `global/`: widely reused primitives, no subfolders, prefixed `Base` (for example `BaseButton`).
- `Layout/`: only used by layouts; `App` prefix if they take props, `The` prefix if they are singletons.
- Page components: a last resort for splitting an unmanageable page, prefixed with the page name.

## Typed API client layer

`frontend/app/lib/api/base/base-clients.ts` defines the base classes: `BaseAPI` (holds an `ApiRequestInstance`), `BaseCRUDAPIReadOnly` (`getAll` with page/perPage/query params, `getOne`) and `BaseCRUDAPI` (adds `createOne`, `updateOne`, `patchOne`, `deleteOne`, `duplicateOne`). Concrete clients in `lib/api/user/`, `lib/api/admin/` and `lib/api/public/` extend them, and aggregate classes (`UserApiClient` in `client-user.ts`, plus admin and public equivalents) expose each as a property (`recipes`, `households`, `shopping`, `mealplans`, ...). Request and response types come from `lib/api/types/`, which is generated from the backend Pydantic schemas and must not be edited by hand (see [[schemas-and-codegen]]).

`app/composables/api/api-client.ts` wires these to Vue: `useRequests` takes the shared axios instance from the Nuxt app, sets the `Accept-Language` header from the active i18n locale, and returns get/post/put/patch/delete wrappers that never throw; they return `{ response, error, data }`. Callers use `useUserApi()`, `useAdminApi()`, `usePublicApi()` or `usePublicExploreApi(groupSlug)`.

## Axios plugin: tokens and errors

`app/plugins/axios.ts` creates the axios instance (`baseURL: "/"`, `withCredentials`). The request interceptor adds `Authorization: Bearer <token>` from the `mealie.access_token` cookie and an `X-Mealie-Embedded` header when the app is framed. The response interceptor:

- shows `message` bodies as info toasts unless `suppressAlert` is set;
- on a 401 for a request that has a token cookie, is not an auth endpoint (`/api/auth/token`, `/refresh`, `/logout`) and has not been retried, refreshes the token once and replays the request, with concurrent 401s sharing one refresh; non-401 failures on the replay surface as themselves rather than logging the user out;
- turns FastAPI `detail` messages (including validation error arrays) into error toasts;
- on an unrecoverable 401 clears the token and redirects to `/login`, keeping a safe `redirect` target.

## Auth state

`useAuthBackend` (`composables/use-auth-backend.ts`) holds module-level refs for the current user, status (`loading`/`authenticated`/`unauthenticated`) and access token, and schedules the next refresh from the token's own expiry so it self-corrects after sleep. `useMealieAuth` wraps it, exposing `user`, `loggedIn` and sign-in helpers for OIDC callback and reverse-proxy login. Tokens are issued by the backend described in [[auth-and-security]].

Route middleware in `app/middleware/` gates pages: `auth` redirects unauthenticated users to `/login?redirect=...`, with additional guards such as `admin-only`, `advanced-only`, `group-only`, `can-manage-only`, `can-manage-household-only` and `can-organize-only`.

## State and caching

Neither Pinia nor Vuex is a dependency of the frontend (`frontend/package.json` lists neither, and no code calls `defineStore`), so there is no global store library. Shared data (categories, tags, tools, foods, units, labels, cookbooks, households, users) lives in composable "stores" under `composables/store/`, built with `partials/use-store-factory` and module-level refs, each with a `reset*Store` function. `useAuthBackend` imports `clearAllStores` and `clearComposableCaches` so logging out clears them. Prefer composables for shared logic and state over new stores.

## Dev proxy

In development, the Nitro handler `frontend/server/api/[...].ts` proxies `/api/*` to `runtimeConfig.apiUrl` (`API_URL`, default `http://localhost:9000`), except `/api/auth/oauth`, which is a redirect so the browser reaches the backend for the OIDC flow.

## i18n and theming

`nuxt.config.ts` lists locales (generated between `CODE_GEN_ID: MESSAGE_LOCALES` markers) loaded lazily from `app/lang/locales`, with `no_prefix` strategy, default `en-US` and cookie-based browser language detection. Only `en-US` strings should be edited by hand; other locales are managed through Crowdin. Theme colors are overridable through `THEME_*` environment variables in `runtimeConfig.public`, and `SUB_PATH` sets the base URL for subpath deployments. Frontend tests are described in [[testing]].
